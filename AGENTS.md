## Repository Purpose

This repository is the canonical `0.2.0+` boilerplates template library consumed by the Boilerplates application.

## Branch Notes

## Template Metadata

- Every `template.json` must declare a nonempty `kinds` array of unique canonical classifications, not scalar `kind`. Multiple kinds are allowed when the authored bundle covers them; the first supplies the fallback icon.
- Every `template.json` must declare `"schema": "boilerplates/template/v1"` at the top level.
- Do not add `metadata.version`; Boilerplates assigns numbered template revisions. Keep dependency versions in authored files or variable defaults.

- For `metadata.icon`, prefer matching existing templates for the same product before choosing a new icon.
- Supported icon providers in the Boilerplates app are `simple-icons`, `devicon`, `mdi`, `tabler`, `ant-design`, `lucide`, and `selfhst`.
- Supported icon colors are `default`, `blue`, `sky`, `violet`, `fuchsia`, `emerald`, `amber`, `orange`, `rose`, and `cyan`; the backend also accepts `inherit` where applicable. Do not use unsupported color names such as `green`.

## Template Variable Metadata

- Supported variable types are `str` (text), `int` (whole number), `float` (decimal number), `bool` (true/false), `enum` (configured option), `email` (validated email address), `url` (validated URL with scheme and host).
- Use JSON integers for `int` defaults. Use `float` for decimal values such as fractional CPU limits; float defaults may be numeric values or strings parseable as decimals.
- Never define credential inputs, `secret` types, `generator`, or `autogenerated` settings. Ordinary inputs may hold external resource names or environment-variable names, never passwords, tokens, hashes, keys, or credential-bearing URLs.
- Never generate `.env` files or credential content, including in ZIP downloads. Compose/Swarm credentials use `${NAME:?Set NAME}` with no defaults; non-sensitive environment settings may use `${NAME:-<< ordinary_variable >>}`.
- Use native downstream credential references: existing Kubernetes Secrets/ExternalSecret resources, Ansible controller environment lookups, provider authentication environments, and Packer runtime variables. Never insert shell interpolation into formats that do not evaluate it.
- For core maintainers with private docs access, the canonical variable reference is [`docs/app/features/templates/templates-variables.md`](docs/app/features/templates/templates-variables.md).
- Only add variable `description` text for specific or unusual settings that need extra explanation for the user.
- For normal/self-explanatory settings, prefer a clear `title` plus a useful `placeholder`; add a `default` only when it is intentionally requested or genuinely useful.
- Do not add descriptions or defaults to every variable by default.
- String variables must render directly as `<< variable >>`; never use inline boolean fallback expressions like `<< variable or 'xyz' >>`, because they can render as `True`. Make the variable required when appropriate, or use an explicit conditional fallback such as `<%- if variable %><< variable >><%- else %>xyz<%- endif %>`.

## Technology File Conventions

Kinds classify bundles; the current application does not require technology-specific entrypoints or initialize files. The following filenames are library conventions, not application validation rules (directory names may use older technology names):

- `compose`: `files/compose.yaml`
- `swarm`: `files/compose.yaml`
- `helm`: `files/values.yaml`
- `kubernetes`: `files/main.yaml`
- `terraform`: `files/main.tf`
- `packer`: `files/main.pkr.hcl`
- `ansible`: `files/main.yml`
- `bash`: `files/main.sh`
- `python`: `files/main.py`
- `static`: no required entrypoint file

Additional regular files may be added under `files/` as needed.

## Validation

- Run `python3 tests/check_kinds.py` and `python3 tests/check_helm_metadata.py` from this repository root for metadata changes. Validate complete bundles with the current application's importer.
- The commands below document the older CLI only; it uses retired kind identifiers and does not validate the current `kinds` manifest contract.
- The validate command requires either one template slug or `--all`.
- Template/Jinja validation always runs.
- Add `--semantic` to render the dependency matrix and run semantic checks for every generated case.
- Add `--kind` to also run the kind-specific validator when a local validator tool is available. If no applicable validator or rendered kind files are available, the result may be reported as `skip` with a warning.
- For a specific template, run:
  - `boilerplates <kind> validate <template-slug> --semantic --kind`
- For every template of a kind, run:
  - `boilerplates <kind> validate --all --semantic --kind`
- Terraform validation can be slow across all templates; for Terraform changes, validate only the affected template without `--all --semantic`:
  - `boilerplates terraform validate <template-slug> --kind`
- Example commands:
  - `boilerplates compose validate whoami --semantic --kind`
  - `boilerplates compose validate --all --semantic --kind`
  - `boilerplates kubernetes validate core-deployment --semantic --kind`
  - `boilerplates kubernetes validate --all --semantic --kind`
  - `boilerplates terraform validate cloudflare-dns-record --kind`
- After changing templates, run validation for every affected kind before finishing.

## Local Config

- This repository includes a local `config.yaml`.
- The local `config.yaml` must point to this checkout as a `static` library so validation reads this repository directly.
- Do not validate against the git-synced library under `~/.config/boilerplates/libraries/...`.
- Run validation from the repo root so `boilerplates` picks up `./config.yaml` instead of the global config.
